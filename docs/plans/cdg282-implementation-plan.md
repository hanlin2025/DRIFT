## Versioned scenario contract: `cdg279.synthetic-disruption.v1`

Implement this contract as test fixture metadata around existing DTOs, with version and explicit provenance; do not introduce parallel shipment/AIS/evidence payload schemas. Inputs contain no estimated arrival, risk level, remaining window, impact result or generated explanation. Expected outputs belong in assertions/a separate expectation table only.

Shared itinerary: fictional origin/destination strings; port `Synthetic Multi-source Port`; planned mother arrival `2026-10-01T06:00:00Z`; planned feeder departure `2026-10-02T12:00:00Z` (30h planned window). Reuse `shipment/SyntheticPortCatalogTestConfiguration.java`: coordinates **longitude 103.82, latitude 1.26**. This port exists only in test configuration; without it production correctly returns `UNKNOWN_PORT`.

Use uniquely namespaced names, e.g. `CDG279 SYNTHETIC MOTHER <run>` and `CDG279 SYNTHETIC FEEDER <run>`, with fixture-assigned nine-digit MMSIs `990279001` and `990279002`. These are fictional labels, not claims about reserved/unassigned real identifiers. Omit optional IMOs/operators rather than invent verified identities. Both shipments use exactly these vessel names/IDs and the same schedule; references `DEMO-CDG279-<run>-A/B`. Names remain stable throughout one run. The manifest explicitly binds both shipments to the same mother-to-feeder visit; that association is a fixture assumption, not AIS evidence of cargo carriage.

Create a dedicated forwarder company/account and linked importer company/account using the existing test setup pattern. Record A's deadline `2026-10-01T12:00:00Z`, B's `2026-10-02T10:00:00Z`, both confirmed for the same port. This difference alone produces differentiated impact; urgency, cargo, inventory, financial exposure and final-delivery deadlines remain unknown.

### Three ordered snapshots

Each stage clock equals the new report's `ingestedAt`. For this constructed scenario `observedAt == receivedAt == ingestedAt` explicitly; zero ingestion lag is a simplifying assumption. All mother longitudes are 103.82. Set `positionValid=true`, navigational status `0` (under way), course/heading `180`, AIS UTC second `0`. Feeder reports at each cutoff can remain at port `(1.26, 103.82)`, SOG `0`, status `5` (moored), course/heading unknown. They provide role/state completeness but do not drive mother-arrival risk. Feeder zero speed is not an unavailable **mother** estimate.

| Stage | Cutoff / mother report time UTC | Mother latitude / SOG knots | Calculated ETA UTC (approximately) | Remaining / risk | Deadline comparison A / B |
| --- | --- | --- | --- | --- | --- |
| 0 baseline | Oct 1 00:00 | 2.26 / 10 | Oct 1 06:00 | 30h / LOW | NO_PREDICTED_IMPACT / NO_PREDICTED_IMPACT |
| 1 material slowdown | Oct 1 04:00 | 1.86 / 3 | Oct 1 16:00 | 20h / MEDIUM | EXCEEDS_DEADLINE / NO_PREDICTED_IMPACT |
| 2 worsened connection | Oct 1 08:00 | 1.66 / 1 | Oct 2 08:00 | 4h / HIGH | EXCEEDS_DEADLINE / NO_PREDICTED_IMPACT |

Distances under the existing formula are approximately 60, 36 and 24 nautical miles. Expected planned window stays 108000 seconds; remaining windows approximately 108000, 72000, 14400 seconds. Use independently documented numeric expectations with <=1ms timestamp/duration tolerance for floating point and database precision, exact risk/outcome assertions, and exact input/schedule equality. Do not derive all expected answers by calling the calculator under test. All selected risk bases must be `AIS_STRAIGHT_LINE_ARRIVAL_ESTIMATE`, all main-path estimates fresh. These are estimates, never verified actual arrival or confirmed missed bookings. No handling minimum/cutoff offset is modeled: planned departure is the comparison boundary, with zero extra handling allowance explicitly a limitation rather than a new computed fact.

Evidence additions (normalized `MaritimeEvidence`, identical source rows for A/B at the same stage):

- Stage 0: no maritime evidence. Risk/impact still calculate; an assessment request abstains `INSUFFICIENT_EVIDENCE` without invoking a client.
- Stage 1: one fictional MPA-style expected-arrival revision, ID `cdg279-v1-revision-1`, retrieved/observed at stage 1 cutoff; previous `2026-10-01T06:00:00Z`, revised expected `2026-10-01T15:00:00Z`. Deliberately different from the AIS estimate to prove no substitution. Use existing `MPA_ETA_REVISION`, role `MOTHER`, observation type `EXPECTED_ARRIVAL`, scope `VESSEL_OBSERVATION`.
- Stage 2: retain revision 1; add a fictional port-area notice `cdg279-v1-notice-2` and regional weather `cdg279-v1-weather-2`, observed/retrieved at stage 2 cutoff. Notice effective window Oct 1 08:00Z through Oct 2 12:00Z, scope `PORT_CONTEXT`; weather scope `REGIONAL_CONTEXT`. Include a different-area incompatible notice as a negative control, excluded from inference. No port/weather value claims to cause the slowdown or quantitatively change risk.

Use source types already supported by the existing fixtures, but **every** row has `sourceMode=SYNTHETIC_DEMONSTRATION`, synthetic title/sourceIdentifier/citation, `https://example.invalid/cdg279/...`, explicit fictional limitation, compatibility dimensions, sufficiency and review flags. `VERIFIED` association is permissible only in the existing all-synthetic sense and must be explained as fixture-defined. `FRESH` is relative to the simulated cutoff; include stale/unknown negative cases. Source-event time is null unless explicitly created; notice effective time is not publication time. Source records and visit/shipment-association metadata remain separate. No authentic file or collector output is rewritten or relabeled.

## Data flow and isolation

1. Guard a newly created disposable database and explicit test profile **before Spring/Flyway startup**, using the existing `ShipmentConstraintDatabaseGuard` pattern. No default `drift`/shared `drift_test` database. Explicitly disable AIS streaming, risk activation/evaluation/mail/dispatch, configured real AI client, and authentic external-processing approvals. Bind the offline client in test configuration.
2. Authenticate; create both shipments, link importer, save importer-owned deadlines through existing endpoints. Seed only constructed AIS with `LatestAisPositions.record`; it persists through the real repository. Do not seed calculated response fields or risk tables.
3. For each ordered stage: set shared clock, validate stage inputs, record its mother/feeder observations, GET normal detail/list, GET maritime context, optionally POST assessment. The normal path is `ShipmentConnectionRisk -> ArrivalEstimateCalculator -> ConnectionWindowService -> ShipmentRisk`; detail also calls `DelayComparison.of`. Assessment consumes these authorized outputs; it never recalculates or changes them.
4. Stages 1/2 use the offline client and real validator/persistence. Retain generated snapshots; historical GET must preserve its original risk/business/evidence facts after advancing stages or changing a deadline. A stub proves integration and grounding, not real-model quality.
5. Roll back tests, close/reset the context/cache, and drop only the explicitly owned disposable database in runner cleanup (also on failure). Re-run starts at stage 0. No `@Commit`, production archive/delete, human-decision mutation or alert activation. For observation-ingestion steps only the intended synthetic observation rows may change; detail/assessment requests may persist assessment rows only. Compare unrelated sentinel records before/after.

## Required automated acceptance tests

- Fixture validation: version/IDs, two contexts, three strictly ordered stages; required vessel/visit links and source provenance; duplicate identical ingestion idempotent, conflicting duplicate/backward stage rejected; coordinates/speed/timestamps valid; no future receipt/retrieval/observation available. Invalid metadata fails before persistence. A late-arriving older **receipt** must not replace the selected latest AIS record; preserve production retention semantics rather than asserting global ingestion deduplication.
- Real engine: exact LOW -> MEDIUM -> HIGH and approximate ETA/windows above for both shipments, unchanged 30h planned window, matching list/detail risk, same AIS/source evidence for A/B; A's impact changes while B's remains clear. Assert schedules/constraints unchanged throughout reads/generation. Changing only MPA-style revised ETA or port/weather evidence leaves numeric AIS risk and impact unchanged.
- Missing/boundaries: no mother position, missing/low SOG, unknown port, stale >6h and exactly 6h, absent deadline and mismatched port. Assert existing unavailable reasons and planned-window fallback, never fabricate a remaining window. Keep <=12h/24h and missed-window threshold coverage in existing unit suites; add a scenario-specific assertion only if integration exposes a new seam.
- Grounding: stage 0 abstains without client invocation; stages 1/2 produce validated offline risk/business claims from supplied facts. Incompatible and future records excluded. Same eligible rows across A/B; only authorized deadline/comparison differs. Historical stage 1 persists unchanged after stage 2. Unsupported causal claim rejected by the existing validator.
- Authorization: unauthenticated 401; unrelated/former importer denied according to existing 403/404 contract for detail, evidence and assessment/history; only current linked importer can edit its deadline. Denied requests never invoke client or persist assessment. Reassignment cannot expose old importer's constraint snapshot.
- Isolation: unrelated/live-like sentinel shipments, authentic source fixtures, schedules, alert state/transitions/deliveries and human decisions unchanged. Only synthetic observation insertion and intended assessment persistence occur. No HTTP/provider invocation, no live AIS connection, no mail. Two complete runs produce identical normalized outputs with run-specific IDs excluded; earlier-stage reads on a fresh run contain no later evidence/cache entries.

Run new tests via the guarded runner, then existing arrival/window/risk/constraint/delay tests and `MaritimeAiCrossShipmentEvaluationIntegrationTests`, `MaritimeAiConnectionRiskContextTest`, `MaritimeAiResponseValidatorTest`, `ConfiguredMaritimeAiClientTest`. Existing database-guarded suites need their own fresh targets/runner settings; do not combine incompatible guarded contexts into one reused database. No frontend changes or paid smoke test are required. Record actual results and exact integration SHA in the runbook; the audit did not execute application tests.
